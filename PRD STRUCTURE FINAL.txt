1. LATAR BELAKANG, TUJUAN, TARGET & KPI

1.1 Latar Belakang
Perkembangan transaksi jual-beli online di Indonesia terus meningkat, namun
banyak pelaku usaha kecil dan menengah (UKM) belum memiliki platform
e-commerce sendiri karena kompleksitas dan biaya pengembangan yang tinggi.
"Web E-Commerce-Mini" hadir sebagai solusi platform jual-beli online skala
kecil-menengah yang ringan, cepat dibangun, dan mudah dikelola, dengan fokus
pada fitur inti: katalog produk, transaksi checkout, dan pembayaran online
melalui payment gateway Midtrans.

Produk ini dirancang sebagai aplikasi fullstack menggunakan Next.js 16,
sehingga frontend dan backend berada dalam satu codebase, mempercepat proses
development dan deployment terutama untuk kebutuhan MVP (Minimum Viable
Product).

1.2 Tujuan Produk (MVP)
- Menyediakan platform e-commerce mini yang fungsional untuk menjual produk
  secara online.
- Memungkinkan customer melakukan browsing katalog, melihat detail produk,
  checkout, dan membayar secara online melalui Midtrans tanpa perlu
  membangun halaman pembayaran custom.
- Menyediakan admin panel sederhana untuk mengelola produk, kategori, dan
  pesanan melalui interaksi modal/pop-up agar development lebih ringkas.
- Membangun fondasi teknis yang aman, scalable, dan mudah dikembangkan lebih
  lanjut ke Phase 2.

1.3 Target Pengguna
a. Customer (End User) - individu yang ingin berbelanja produk secara
   online, melakukan pencarian produk, checkout, dan pembayaran.
b. Admin (Pengelola Toko) - pemilik/pengelola bisnis yang bertanggung jawab
   mengelola master data produk, kategori, pesanan, dan pengaturan toko.

1.4 Success Metrics (KPI)
- Checkout Completion Rate >= 60% dari total transaksi yang dimulai.
- Payment Success Rate via Midtrans >= 95%.
- Rata-rata waktu load halaman katalog/produk < 2 detik (jaringan standar).
- Admin dapat menyelesaikan 1 siklus CRUD produk (create-update-delete)
  dalam < 1 menit menggunakan modal.
- Uptime aplikasi >= 99% pasca-deployment di Hostinger.
- Zero critical security incident pada modul autentikasi dan pembayaran
  selama 3 bulan pertama pasca-launch.

3. BUSINESS RULES

1. Customer wajib login/register sebelum menyelesaikan proses checkout
   (guest checkout tidak didukung di MVP).
2. Produk hanya dapat dibeli jika stok > 0. Sistem menolak checkout untuk
   produk dengan stok habis.
3. Harga produk yang berlaku adalah harga pada saat produk ditambahkan ke
   checkout, bukan harga real-time saat pembayaran dikonfirmasi.
4. Setiap proses checkout menghasilkan 1 Order dengan status awal PENDING
   sebelum customer diarahkan ke Midtrans.
5. Status Order hanya boleh berubah menjadi PAID setelah menerima notifikasi
   valid dari Midtrans (via webhook/callback), bukan berdasarkan aksi
   redirect front-end semata.
6. Stok produk otomatis berkurang setelah status Order menjadi PAID (bukan
   saat checkout dibuat), untuk menghindari stok "tersandera" oleh transaksi
   yang belum dibayar.
7. Order yang tidak dibayar dalam batas waktu tertentu (mengikuti masa aktif
   transaksi Midtrans, default 24 jam) otomatis berubah status menjadi
   EXPIRED.
8. Hanya user dengan role admin yang dapat mengakses admin panel dan
   melakukan operasi CRUD terhadap produk, kategori, dan pesanan.
9. Admin tidak dapat menghapus permanen produk yang masih terikat pada Order
   aktif (histori transaksi harus tetap konsisten) - sistem menggunakan soft
   delete/nonaktifkan (isActive = false) untuk produk yang sudah pernah
   terjual.
10. Email wajib unik untuk setiap akun, baik customer maupun admin.

5. USER FLOW (ALUR END-TO-END)

5.1 Customer Flow

[Homepage] -> [Catalog] -> [Detail Halaman Produk] -> [Login/Register]
   -> [Checkout] -> [Midtrans Payment Page] -> [Redirect] -> [Homepage]

Detail:
1. Customer membuka Homepage, melihat produk unggulan/kategori.
2. Customer masuk ke Catalog untuk melihat semua produk / melakukan
   pencarian & filter.
3. Customer klik produk -> masuk ke Detail Halaman (deskripsi, harga,
   stok, gambar, tombol beli/checkout).
4. Jika belum login, sistem mengarahkan ke halaman Login/Register terlebih
   dahulu.
5. Setelah login, customer melanjutkan ke halaman Checkout (ringkasan
   pesanan, alamat, metode pembayaran).
6. Sistem membuat Order berstatus PENDING dan generate Midtrans Snap
   Transaction, lalu redirect customer ke halaman pembayaran Midtrans
   (menggunakan Snap page bawaan Midtrans, tanpa halaman success custom).
7. Setelah pembayaran (sukses/gagal/pending), Midtrans mengirim notifikasi
   webhook ke backend untuk update status Order, dan customer diarahkan
   kembali ke Homepage.

5.2 Admin Flow

[Login] -> [Admin Panel: CRUD via Modal] -> [Settings] -> [Logout]

Detail:
1. Admin membuka halaman Login (sistem login sama, dibedakan lewat role).
2. Setelah login berhasil, admin diarahkan ke Admin Panel (dashboard ringkas
   + tabel data).
3. Admin melakukan operasi Create/Update/Delete pada produk, kategori, dan
   pesanan melalui pop-up/modal di atas halaman yang sama (tanpa reload
   halaman penuh) agar workflow lebih cepat dan sederhana.
4. Admin dapat membuka halaman Settings untuk mengatur konfigurasi dasar
   toko.
5. Admin melakukan Logout untuk mengakhiri sesi.

11. BACKEND ARSITEKTUR

Pattern: Layered Architecture di dalam Next.js API Route Handlers
(folder app/api/**)

app/
 |- api/
     |- auth/
     |    |- register/route.ts
     |    |- login/route.ts
     |    |- logout/route.ts
     |- products/
     |    |- route.ts            (GET list, POST create - admin)
     |    |- [id]/route.ts       (GET detail, PUT update, DELETE - admin)
     |- categories/
     |    |- route.ts
     |    |- [id]/route.ts
     |- orders/
     |    |- route.ts            (POST create order/checkout)
     |    |- [id]/route.ts       (GET detail, PUT update status - admin)
     |- midtrans/
          |- notification/route.ts  (webhook dari Midtrans)
          |- snap-token/route.ts    (generate token transaksi)

lib/
 |- prisma.ts        (Prisma client singleton)
 |- auth.ts          (helper JWT sign/verify, session)
 |- midtrans.ts       (Midtrans client config)
 |- validation/       (Zod schema per entity)

middleware.ts          (proteksi route /admin/** & API admin, verifikasi
                         JWT & role)

Prinsip:
- Setiap route handler memvalidasi input dengan Zod sebelum diproses.
- Service layer memisahkan logika bisnis dari route handler agar mudah
  diuji & di-maintain.
- Prisma Client digunakan sebagai satu-satunya akses ke database (tanpa
  raw query kecuali benar-benar diperlukan).
- Idempotency pada webhook Midtrans (mencegah update ganda jika notifikasi
  dikirim lebih dari sekali).

13. API CONTRACT

Format response standar:
Success : { "success": true, "data": {...} }
Error   : { "success": false, "error": { "code": "STRING", "message": "STRING" } }

13.1 Authentication
POST /api/auth/register
  Body     : { name, email, password }
  Response : 201 { success: true, data: { id, name, email } }

POST /api/auth/login
  Body     : { email, password }
  Response : 200 { success: true, data: { token, user: { id, name, email,
             role } } }

POST /api/auth/logout
  Response : 200 { success: true }

13.2 Products
GET  /api/products?search=&category=&page=
  Response : 200 { success: true, data: { items: [...], total, page } }

GET  /api/products/[id]
  Response : 200 { success: true, data: { ...product } }

POST /api/products        (Admin only)
  Body     : { name, categoryId, price, stock, description, imageUrl }
  Response : 201 { success: true, data: { ...product } }

PUT  /api/products/[id]   (Admin only)
  Body     : { name?, categoryId?, price?, stock?, description?, imageUrl?,
             isActive? }
  Response : 200 { success: true, data: { ...product } }

DELETE /api/products/[id] (Admin only)
  Response : 200 { success: true }

13.3 Categories
GET/POST /api/categories, GET/PUT/DELETE /api/categories/[id]
  (Pola sama seperti Products, operasi write khusus Admin only)

13.4 Orders / Checkout
POST /api/orders            (Customer, auth required)
  Body     : { items: [{ productId, quantity }] }
  Response : 201 { success: true, data: { orderId, snapToken,
             redirectUrl } }

GET  /api/orders            (Customer: order miliknya | Admin: semua order)
GET  /api/orders/[id]
PUT  /api/orders/[id]/status (Admin only)
  Body     : { status }

13.5 Midtrans
POST /api/midtrans/notification   (Webhook Midtrans, tanpa auth user,
                                    diverifikasi via signature key)
  Body     : payload notifikasi Midtrans standar
  Response : 200 { success: true }


14. STATE DIAGRAM (STATUS ORDER)

[PENDING] --(settlement/capture)--> [PAID] --(admin proses)--> [PROCESSING]
                                                                     |
                                                                     v
                                                               [SHIPPED]
                                                                     |
                                                                     v
                                                              [COMPLETED]
   |
   |--(timeout/expire dari Midtrans)--> [EXPIRED]
   |--(pembayaran ditolak)--> [FAILED]
   |--(dibatalkan sebelum bayar)--> [CANCELLED]

Detail transisi:
- PENDING -> PAID       : dipicu notifikasi Midtrans (transaction_status =
                           settlement/capture)
- PENDING -> EXPIRED    : dipicu notifikasi Midtrans (transaction_status =
                           expire)
- PENDING -> FAILED     : dipicu notifikasi Midtrans (transaction_status =
                           deny)
- PENDING -> CANCELLED  : dipicu manual oleh customer/admin sebelum bayar
- PAID -> PROCESSING    : diubah manual oleh admin (mulai proses pesanan)
- PROCESSING -> SHIPPED : diubah manual oleh admin
- SHIPPED -> COMPLETED  : diubah manual oleh admin (konfirmasi selesai)

16. ERROR HANDLING

Prinsip umum:
- Semua error API mengikuti format standar (lihat bagian 13) dengan HTTP
  status code yang sesuai.
- Validasi input menggunakan Zod; error validasi dikembalikan sebagai 400
  Bad Request dengan detail field yang gagal.

+---------------------------+------+-----------------------------------+
| Kasus                     | Code | Pesan                              |
+---------------------------+------+-----------------------------------+
| Validasi input gagal       | 400  | "Validation error" + detail field  |
| Belum login/token invalid  | 401  | "Unauthorized"                     |
| Role tidak sesuai          | 403  | "Forbidden: admin only"            |
| Data tidak ditemukan       | 404  | "Resource not found"               |
| Email sudah terdaftar      | 409  | "Email already registered"         |
| Stok tidak cukup           | 409  | "Insufficient stock"                |
| Signature Midtrans invalid | 401  | "Invalid notification signature"    |
| Server error tak terduga   | 500  | "Internal server error"             |
+---------------------------+------+-----------------------------------+

Frontend:
- Menampilkan toast/alert untuk setiap error dari API dengan pesan yang
  human-readable (bukan raw error message backend).
- Form menampilkan error per-field hasil validasi Zod (schema client-side
  & server-side sinkron).


17. SECURITY REQUIREMENT

1. Password di-hash menggunakan bcrypt (salt rounds >= 10), tidak pernah
   disimpan/di-log dalam bentuk plain text.
2. Autentikasi menggunakan JWT dengan masa berlaku terbatas (mis. 7 hari)
   disimpan di httpOnly cookie (mencegah akses via JavaScript/XSS).
3. Middleware Next.js memvalidasi token & role pada setiap request ke route
   admin dan API sensitif.
4. Semua input divalidasi & disanitasi menggunakan Zod, baik di client
   maupun server (server-side validation wajib, client-side untuk UX).
5. Endpoint webhook Midtrans (/api/midtrans/notification) wajib
   memverifikasi signature key sesuai dokumentasi Midtrans untuk memastikan
   notifikasi valid dan bukan dari pihak tidak dikenal.
6. Environment variable (kredensial DB, JWT secret, Midtrans Server Key)
   disimpan di .env dan tidak pernah di-commit ke repository.
7. Proteksi terhadap SQL Injection otomatis tercapai melalui penggunaan
   Prisma ORM (parameterized query).
8. Rate limiting sederhana pada endpoint login/register untuk mencegah
   brute force.
9. HTTPS wajib diaktifkan di environment production (SSL dari Hostinger).
10. CORS dikonfigurasi ketat, hanya mengizinkan origin resmi aplikasi.


18. DATABASE CONSTRAINT

- User.email          : UNIQUE, NOT NULL
- User.role            : ENUM('ADMIN','CUSTOMER'), NOT NULL, default
                          CUSTOMER
- Product.slug         : UNIQUE, NOT NULL
- Product.price        : DECIMAL, NOT NULL, CHECK (price >= 0)
- Product.stock        : INTEGER, NOT NULL, default 0, CHECK (stock >= 0)
- Category.slug        : UNIQUE, NOT NULL
- Order.status          : ENUM('PENDING','PAID','PROCESSING','SHIPPED',
                          'COMPLETED','FAILED','EXPIRED','CANCELLED'),
                          NOT NULL, default PENDING
- Order.userId           : FOREIGN KEY -> User.id, ON DELETE RESTRICT
- OrderItem.orderId       : FOREIGN KEY -> Order.id, ON DELETE CASCADE
- OrderItem.productId     : FOREIGN KEY -> Product.id, ON DELETE RESTRICT
- Payment.orderId         : FOREIGN KEY -> Order.id, UNIQUE (1-to-1),
                            ON DELETE CASCADE
- Product.categoryId      : FOREIGN KEY -> Category.id, ON DELETE RESTRICT
                            (kategori tidak bisa dihapus jika masih ada
                            produk aktif)

23. ACCEPTANCE CRITERIA

AC-1 Register
- Given customer belum memiliki akun, When mengisi form register dengan
  data valid, Then akun berhasil dibuat dan customer dapat login.
- Given email sudah terdaftar, When mencoba register dengan email yang
  sama, Then sistem menampilkan error "Email already registered" dan
  tidak membuat akun baru.

AC-2 Login
- Given customer/admin memiliki akun valid, When login dengan email &
  password benar, Then sistem mengembalikan token & mengarahkan sesuai
  role (customer -> homepage, admin -> admin panel).
- Given kredensial salah, When mencoba login, Then sistem menampilkan
  error dan tidak memberikan akses.

AC-3 Checkout & Pembayaran
- Given customer login dan produk tersedia (stok > 0), When melakukan
  checkout, Then sistem membuat Order berstatus PENDING dan mengarahkan
  ke halaman pembayaran Midtrans.
- Given pembayaran berhasil di Midtrans, When webhook notification
  diterima dan signature valid, Then status Order berubah menjadi PAID
  dan stok produk berkurang sesuai quantity.
- Given produk stok habis, When customer mencoba checkout produk
  tersebut, Then sistem menolak dan menampilkan pesan "Insufficient
  stock".

AC-4 Admin CRUD Produk
- Given admin login, When membuka Admin Panel dan klik "Tambah Produk",
  Then modal form muncul tanpa reload halaman.
- Given admin mengisi form produk dengan data valid dan submit, Then
  produk baru tersimpan dan langsung muncul di tabel/list tanpa reload
  halaman penuh.
- Given admin menghapus produk yang belum pernah terjual, Then produk
  terhapus dari list dan tidak lagi tampil di catalog customer.

AC-5 Role-Based Access
- Given user dengan role customer, When mencoba mengakses route /admin,
  Then sistem menolak akses (redirect/403).
- Given user belum login, When mencoba mengakses halaman checkout, Then
  sistem mengarahkan ke halaman login terlebih dahulu.
